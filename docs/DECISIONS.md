## D2 — FHIR client: httpx + fhir.resources
`fhir.resources` gives Pydantic v2 models for R4 (we use the `fhir.resources.R4B`/R4 subpackage —
to be verified in M1 against the installed 8.x layout). httpx for transport (sync + async).
Chosen over `fhirclient` because it fits our Pydantic v2 stack and structured outputs.

## D3 — HAPI persists to the shared Postgres (separate `hapi` database)
Keeps loaded Synthea data across restarts. No in-container HAPI healthcheck (image contents
unverified); readiness via `scripts/check_services.py`. To verify once Docker is installed.

## D4 — Offline FHIR checks use R4B models (M1)
`fhir.resources` 8.3.0 ships R5 (default), R4B and STU3; there is no R4 package. For every
resource we generate (Patient, Coverage, Condition, Observation, Procedure, MedicationRequest,
DocumentReference, ServiceRequest, Organization, Practitioner, Bundle) the fields we use are the
same in R4 and R4B. Tests validate offline with `fhir.resources.R4B`; HAPI R4 `$validate`
(`scripts.load_fhir --validate`) is the authoritative check once the stack runs. Not yet run.

## D5 — Case patients are generated by build_cases, not taken from Synthea (M1)
Each eval case gets its own synthetic Patient + Coverage so `build_cases` is reproducible from
its seed without a running server or Synthea. Synthea patients (scripts.generate_patients +
seed_coverage) are background population for the demo. All case resources carry a `case-id` tag.

## D6 — Labelling rules for tricky cases (M1)
- Stale evidence (older than the criterion window) → `missing` (documentation out of date).
- Contradictory notes → `missing` (needs clarification), both notes listed as supporting.
- Terminated coverage → eligible=false; readiness=null. No-PA service → pa_required=false;
  readiness=null. Readiness is only defined when eligible and PA is required.
- Readiness: any not_met → likely_not_meeting_criteria; else any missing → needs_more_info;
  else ready_to_submit.

## D7 — Codes
ICD-10-CM, LOINC (BMI 39156-5, progress note 11506-3), RxNorm ingredient codes, UCUM.
Procedures and non-BMI observations use an internal code system
(`http://acme-health.example/fhir/CodeSystem/clinical`) rather than guessed SNOMED/LOINC codes.
No CPT. Only HCPCS mapping: CPAP → E0601. Synthea pinned to v3.3.0 (verify flags vs README).

## D8 — Intake runs against a FhirSource interface (M2)
`HapiSource` (live) and `BundleSource` (case bundles on disk) share read/search. Evals default to
offline with the mock payer in-process via FastAPI `TestClient`; `--live` uses HAPI + the payer
service. Eval reports record commit hash (or `uncommitted`) and whether the worktree was dirty.

## D9 — CRD documents list (M2)
`/crd/check` returns one required document per policy criterion, derived from criterion kind,
plus the policy's documentation section id (e.g. `LSMRI-5`). Eligibility is not the payer's job
in this mock; the payer CRD only answers "is PA required for this service on this plan".

## D10 — Who decides what (M3)
Structured criteria (codes, dates, durations, counts, thresholds) are found and judged by plain
code. The LLM only reads free-text notes, returns quotes with a stance (supports / contradicts)
under a strict JSON schema; code locates each quote to compute its character span. LLMs are
unreliable at offsets, so spans are never taken from the model.

## D11 — Retrieval design (M3)
One chunk per policy section with a heading breadcrumb. Queries: one for the service's coverage
criteria + one per document the payer's CRD response lists; rankings fused with RRF (k=60);
a retrieved "X-2 Coverage criteria" heading expands to its children. A criterion not retrieved
is reported as `missing` ("not assessed"), never silently skipped.

## D12 — Prompt-injection defence (M3)
Notes wrapped in <note> tags (embedded closing tags escaped); system prompt treats notes as data;
instruction-like lines are flagged and reported; unknown ids in model output are dropped; quotes
must be verbatim and must not be instruction-like; labels use verified evidence only.

## D13 — Offline extractor (M3)
`FakeLLM` + `heuristic_handler` (keyword overlap, prefix stemming, negation cues) is the default
when no LLM is configured. It is not a language model and every report says so.

## D14 — openai SDK 3.51.0
`client.chat.completions.parse(response_format=<Pydantic>)` for structured outputs, temperature 0.
Same code path for Azure (`AzureOpenAI`) and OpenAI-compatible endpoints. Not yet called live.

## D15 — Approval gate lives in the audit store (M4)
`submit_packet` re-reads the approval event from the audit store and checks action, role
(`pa_reviewer`), thread id and sha256 of the exact packet. Editing criteria rebuilds the packet
and voids earlier approvals. The workbench takes the role from the session, never the form.

## D16 — Checkpointer (M4)
SQLite (`langgraph-checkpoint-sqlite` 3.1.3) file under `data/runtime/` locally so review
survives restarts without Docker; `CHECKPOINTER=postgres` switches to
`langgraph-checkpoint-postgres` 3.2.1 (spec target). Graph state is plain JSON.

## D17 — Packet shape (M4)
Bundle type `collection`: Claim (use=preauthorization, status active, type professional) with
one `supportingInfo` per verified evidence item; category code = policy criterion id (internal
code system); note quote/span/stance in extensions. Cover summary = Claim.text narrative.

## D18 — Mock payer decision (M4)
Payer re-evaluates attached evidence itself with the policy rules (it ignores the provider's
labels): coverage inactive → denied ACME-D03; any criterion not met → denied ACME-D01; any
missing → pended ACME-P01; else approved with a pre-auth ref. Mock-only header
`X-Reviewer-Approval` makes the approval invariant observable on the payer side.
